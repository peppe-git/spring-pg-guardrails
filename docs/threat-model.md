# Threat model

## What is protected

Tenant data in a PostgreSQL database shared by many tenants, read and written by a Spring application.

## The adversary this library is for

**The application's own bugs**, which are the realistic way tenant data leaks:

| Threat | Mitigation | Verified by |
|---|---|---|
| A query forgets `WHERE tenant_id = ?` | Policies filter every statement | `RlsIsolation` |
| A new tenant table is created without RLS, or without `FORCE` | — | `RlsCoverage` |
| A policy compares with nothing, or its `WITH CHECK` accepts any tenant | Policies generated by `enable_tenant_rls()` | `RlsCoverage`, `RlsIsolation` |
| An admin escape lets cross-tenant writes or deletes through | Escape only in `FOR SELECT`, only in `READ ONLY` transactions | `RlsCoverage`, `RlsIsolation`, `applyAdminRead()` |
| The tenant is never written, or written on an auto-commit connection | Listener at transaction begin; `TenantGuc` refuses auto-commit; strict mode raises | `TenantGucJdbcIT`, strict mode |
| A pooled thread or connection carries the previous tenant | Scopes always restore; setting is transaction-local | `TenantContextTest`, `TenantGucJdbcIT` |
| The runtime role gets `BYPASSRLS`, superuser, a privileged membership or ownership | — | `RuntimeRoleCheck` (start-up), `RuntimeRoleVerifier` |
| Tests pass because they run as a superuser | Guards switch to a non-superuser role | `RlsIsolation`, `RlsProbe` |
| A guard is green because it looked at nothing, or an exemption outlived its reason | Floor and two-way exemptions in every guard | `GuardEngineTest` |

## Out of scope (non-guarantees)

- **SQL injection.** The tenant setting is an ordinary custom GUC: any SQL that runs as the runtime role can write it
  (`set_config('app.current_tenant', '<victim>', true)`), and can open the admin escape. RLS raises the cost of an
  application bug; it does not contain an attacker who executes SQL. Parameterised queries remain mandatory.
  A stronger admin path is a separate login role with a `FOR SELECT ... TO admin_reader` policy, used by a separate
  `DataSource`, with the runtime role not a member of it.
- **Privileged connections.** Superusers, `BYPASSRLS` roles and owners of non-forced tables bypass policies.
  `RuntimeRoleCheck` warns or refuses to start; anything else that connects (BI tools, scripts, replicas) is yours
  to control.
- **Views and functions.** A view runs with its owner's privileges unless created with `security_invoker = true`
  (PostgreSQL 15+); a view owned by a superuser shows every row. `SECURITY DEFINER` functions run as their owner.
  Planned as guards for v0.2; review them by hand until then.
- **Side channels.** Unique constraints are global: inserting a duplicate key reveals that the key exists in
  another tenant. Sequences, statistics, timing and error messages can leak counts or existence. Scope unique
  constraints by tenant (`unique (tenant_id, email)`) where existence is sensitive.
- **Data outside the database**: caches, search indexes, object storage, logs, backups. RLS does not reach them.
- **Strict mode on empty scans.** A statement that evaluates no policy (empty table) returns zero rows without
  error.
- **Transactions outside Spring's managers** (plain JDBC with auto-commit off, other frameworks): no automatic
  setting; strict mode is the safety net.
- **Heuristic guards.** `OnConflictHasArbiter` reads SQL from source text; dynamically built statements are reported
  as inconclusive, never as green.

## Assumptions

- Migrations run as a role different from the runtime role.
- The runtime role's password and the database network are protected by the infrastructure.
- The tenant identifier written by the application has been authenticated and authorised before it is bound.
